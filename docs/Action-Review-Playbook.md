# Action 审查手册（Review Playbook）

本文沉淀对 `fe-tools-bundler-session` 进行的 14 轮审查的维度、方法与经验，作为后续 Action（或等价工作单元）审查的可复用框架。案例来源标注为 `[BS]`（fe-tools-bundler-session）。

与 [Experience-Review.md](./Experience-Review.md) 的分工：那边是**开发与排查**的通用经验（层级定位、消融、回归验证）；本文是**工作单元审查**的方法论——审范围、审契约、审落地、审验收。

## 1. 审查维度总表

14 轮收敛为六个维度族；同角度复审降至纯 L 级 findings 即为该维度收敛信号。

| 轮 | 维度族 | 角度 | 核心问题 | 代表 findings `[BS]` |
| --- | --- | --- | --- | --- |
| 1 | 边界 | 纳入/排除 | 该纳入有没有漏？不该纳入有没有越界？ | file 层为不存在的产物而定义（M）；dev 的 buildId 状态归属未划（M） |
| 2 | 边界 | 收窄后自洽 | 收窄/修改后内部是否矛盾？与源码对不对得上？ | 优先级文案仍含已删除的层（M）；委托函数复用形状未写清（M）；验收基线混淆既有/新增（M） |
| 3 | 边界 | 生命周期/入口唯一性 | 失败路径、并发状态、配置入口是否唯一？ | dev 启动中途失败无回滚（M）；host/port 绕过 resolve 的第三入口（M） |
| 4 | 边界 | 落地能力/演化 | 承诺的行为能否落在真实源码上？留的锚点是否妨碍后续？ | lifecycle 无 off → 监听残留（成文接受，M）；watcher.stop 存在性核实（✓） |
| 5 | 可行性 | 门/映射/fixture | 计划粒度够不够？CLI 映射完整吗？测例基础设施在吗？ | 产品门缺 acceptance/CLI 接线映射（M）；flags→resolve 层映射未成文（M） |
| 6 | 可行性 | 模块接线 | import 方向、私有函数可达性、判据与"行为不变"一致？ | 主入口委托成 ESM 循环（M）；冒烟判据超出行为不变范围（M）；辅助函数迁移有环（M） |
| 7 | 可行性 | 缺省值 1:1 | 每个 flag 的缺省语义接线前后等价吗？ | CLI `-s` 缺省=cwd vs resolve 回落=workPath，1:1 破坏点（M）；checklist 错标（L） |
| 8 | 适配性 | 静态断言（Source Audit） | 文档对源码的每个事实断言逐条核对 | stages 清单 13/13 通过；2 个可接受近似偏差记录在案 |
| 9 | 适配性 | 执行路径+可写性 | 运行时传播路径、命令面完整、fixture 模板 | rebuild 的 lifecycle 传播（✓）；成功编译 fixture 模板确认（✓）；wsPath 未成文（L） |
| 10 | 功能完整性 | 问题→交付覆盖 | 声明的缺口每条有交付物承接吗？用户旅程有盲区吗？ | 缺口③「lifecycle 非经会话暴露」无任何承接（M）；导出位置双盲区（M） |
| 11 | 文件规划 | 拓扑/清单 | 依赖图有环吗？测试文件规划了吗？目标文件清单齐吗？ | **两轮独立决策的交互产物成环**（M，fail 级）；测试文件名缺失（L） |
| 12 | 文件规划 | 完备性/验证链 | 清单枚举有遗漏吗？新增验证有命令覆盖吗？ | 不动清单缺兜底句（L）；exports entry 无 validation 命令（L） |
| 13 | 验收/闭环 | 判据层 | 验收条目客观可判定？闭合条件成文？消融覆盖？ | Closure conditions 缺失（M）；"对照可读"主观判据（L） |
| 14 | 验收/闭环 | 机制层 | 证据格式/落点？门级部分验收？已知偏差豁免？ | Result 格式未定（L）；消融证据落点未定（L） |

## 2. 各维度审查方法

### 2.1 边界（4 轮）

**审什么**：范围切片本身——纳入/排除清单、与问题陈述的对应、收窄后的自洽、行为序列的完备（成功路径之外还有失败/并发/清理）。

**怎么审**：
- 逐条对问题陈述（Background/缺口）→ Goal → 需求 → 交付物 → 验收，找"声明了但没交付"与"交付了但没声明"。
- 拿真实源码验证每个"今日行为"假设：不存在的输入层不要为它定义规则 `[BS: file 层]`。
- 状态与生命周期：列出所有会话/模块级可变状态（如 activeLoop、计数器、监听器），逐个问失败后去哪、复用时残留什么。
- 入口唯一性：同一配置值列出所有可达路径，超过一条即 finding。

**典型 finding 模式**：为不存在的产物定义规则；状态归属未划（会话 vs adapter）；失败路径半套回滚（清了互斥状态没清发布状态）；第三入口绕过唯一优先级链。

### 2.2 实施可行性（3 轮）

**审什么**：计划能否执行而不需发明决策——粒度、映射、接线方向、缺省值。

**怎么审**：
- **门映射**：每个产品门 → 交付物 + 接线 + 验收子集 + 验证子集 + 门间依赖。缺这张表，实施者自行发明粒度。
- **映射表成文**：CLI flag → resolve 层键 → 变换规则（camelCase、`--no-x` 翻转、路由 flag 不进 resolve）。
- **三层 1:1**：映射（flag→键）→ 接线方向（import 约束、私有函数可达性）→ **缺省值**（每个 flag 接线前后等价）。经验：**argv 缺省值留 bin 显式传**，resolve 只收显式值——resolve 内回落仅服务纯 API 调用者。
- **拓扑推演**：画出目标依赖图；"禁止"语句反向锁死（如禁止主入口 re-export session）。

**典型 finding 模式**：委托路径撞私有函数（只能经 default export → 成环）；冒烟判据引入今日不存在的能力（如 SIGINT 干净退出）；cwd vs workPath 的缺省分歧。

### 2.3 代码适配性（2 轮）

**审什么**：设计文档对源码的事实断言是否失真；运行时传播路径是否如设计所愿。

**怎么审**：
- **静态断言全量核对**：清单类文档（阶段表、函数对照）逐行对源码——函数名、签名（含参数名）、导出形式、条件跳过逻辑、测试文件存在性。近似偏差（参数名、标题后缀）可裁定"记录不修"，但要显式记录，防止后续验证者误判。
- **执行路径核对**：委托链的每一跳（如 session 注入的 lifecycle 是否传播到 rebuild——顺着 `{...options}` 展开逐处确认）；命令注册面；fixture 的错误路径与成功路径模板。
- **script 链分析**：验证命令挂在哪个 script、什么顺序真的跑（如 check-package-exports 挂 postbuild，test 链不覆盖 exports map——需要单独的验收命令补位）。

### 2.4 功能完整性（1 轮）

**审什么**：问题声明的每条缺口是否有交付物与验收承接；用户旅程（CLI/API/兼容导出/细节）有无盲区。

**怎么审**：缺口 × Goal × 需求 × 验收的覆盖矩阵（"持有 ≠ 暴露"这类措辞差异就是断裂点）；按用户类型走完整旅程找漏（如 API 用户挂监听的入口、新导出的 import 位置与验证命令）。

### 2.5 文件规划（2 轮）

**审什么**：实施后的文件布局、依赖拓扑、测试文件、验证命令覆盖。

**怎么审**：
- **拓扑图 + 禁令**：零循环成图示；把"不得 X"写成显式禁令（防止后续轮次的正确决策重新引入环）。
- **三清单**：新增/修改/不动（含兜底句"其余全部不动"）——让 diff 审查有逐行对照基准。
- **验证链补位**：每类新面（新 exports entry、新 API）都要有对应验证命令并确认它真的会被跑。

### 2.6 验收/闭环（2 轮）

**审什么**：判据层（能否客观 pass/fail）与机制层（证据怎么记）。

**怎么审**：
- 每条 acceptance 的 Evidence 列必须可操作（测例名 / grep 模式 / 具体命令）；主观词（"可读""合理"）一律操作化。
- 消融覆盖**全部新增行为**（不只是 bug 修复）；证据四要素成文（目标用例、消融内容、预期与实际失败点、恢复后复验）。
- 机制细则：Result 格式（命令→摘要+日期+commit）；门级部分验收不提前回写终态表；已裁定偏差在对应验证条目显式豁免。

## 3. 关键经验

1. **角度轮换，收敛即停**。同一角度复审，findings 降至纯 L 级 = 该维度收敛 `[BS: 第 12/14 轮]`。继续榨取的边际收益低于换角度。
2. **跨轮决策的交互产物是盲区高发区**`[BS: M-K1]`。两轮各自正确的决策（"default build 不委托"消两节点环 + "主入口 re-export"）组合出结构性循环——**每引入一个新方向性决策，回查既有决策的组合拓扑**。
3. **问题陈述逐条对交付**。"声明了但没交付"是最隐蔽的功能断裂 `[BS: 缺口③]`——措辞差异（持有 vs 暴露）就是线索。
4. **三层 1:1 缺一不可**：flag 映射、接线方向、缺省值——只核前两层会漏 `cwd vs workPath` 这类破坏点。
5. **判据操作化**。"文档审查""对照可读"不可判定；grep 模式、链接检查、测例名才算。
6. **验证链实证**。写了命令不等于有人跑——查它挂在哪个 script、什么顺序触发；test 链不覆盖的面（exports map）要单独补验收命令。
7. **已知限制成文接受优于隐式假设**。不接受修复时，把机理（为何无害）、残留风险（累积）、revisit 条件（A1 加 off）三样写全 `[BS: M-D1]`。
8. **近似偏差显式记录**。Source Audit 发现的参数名/标题差异，裁定"记录不修"后必须在对应验证条目里豁免，防止后续验证者误判 fail。
9. **消融不止于 bug**。重构类工作的每项新增行为（接线、注入、回滚）都可消融且应该消融。
10. **闭环要双层**：判据层（客观性）+ 机制层（证据格式、门级记录、落点）。缺机制层，验收结果不可比、不可审计。

## 4. 快速检查清单

审查一个 Action 时按维度族过一遍（每项都可 grep/对照源码执行）：

```text
边界
  [ ] 问题陈述每条缺口 ↔ 交付物 ↔ 验收 有承接
  [ ] 不为不存在的输入/产物定义规则（对源码核实"今日行为"）
  [ ] 所有会话级可变状态：失败后去向、复用时残留、归属（会话/adapter/调用方）
  [ ] 每个配置值只有一条可达路径（无第三入口）
  [ ] 排除项（Non-goals）与范围表、代码注释三处一致

可行性
  [ ] 产品门映射表（交付物+接线+验收+验证+依赖）
  [ ] CLI flags → resolve 层映射表（含变换与路由 flag）
  [ ] argv 缺省值留 bin 显式传；resolve 回落标注"仅纯 API"
  [ ] 目标依赖图零循环 + 显式禁令；私有函数可达性核实
  [ ] 冒烟判据不超出"行为不变"范围

适配性
  [ ] 清单/对照类文档逐行对源码（函数名/签名/导出/条件/测试存在性）
  [ ] 委托链每一跳的传播核实（如 lifecycle → rebuild）
  [ ] 命令注册面完整；fixture 错误+成功路径模板存在
  [ ] 验证命令的 script 挂载与顺序实证

功能完整性
  [ ] 缺口×Goal×需求×验收 覆盖矩阵满
  [ ] 按用户类型走完整旅程（CLI/API/兼容/细节）
  [ ] 新导出/API 有 import 位置与验证命令

文件规划
  [ ] 拓扑图 + 禁令；测试文件名与门归属
  [ ] 新增/修改/不动 三清单 + 兜底句

验收/闭环
  [ ] 每条 acceptance 的 Evidence 可操作（无主观词）
  [ ] 消融覆盖全部新增行为 + 四要素记录格式
  [ ] Closure conditions 成文（交付/消融/Backflow/一致性）
  [ ] 证据格式、门级部分验收规则、已裁定偏差豁免
```
